# ADR-002: Карта сервисов и доменные границы

## Контекст

Монолит GoFuture содержит 9 логических доменных модулей (Booking, Driver,
Pricing, Payments, Payouts, Notification, Geography, Analytics, Fraud),
которые сейчас живут в одной Django-кодовой базе и работают с единой БД
PostgreSQL. Модули сильно связаны синхронными вызовами (см. C3): Booking
синхронно дёргает Driver, Pricing, Payments, Geography, Fraud и Notification.

Для перехода к микросервисам нужно определить целевые bounded contexts
и зафиксировать их границы. Это будет основой для очерёдности выделения
сервисов (ADR-003) и диаграммы C2 To-Be (ADR-004).

Ключевые ограничения:
- Стек сервисов — Python.
- Payouts и Payments — отдельные домены.
- Горизонтальное масштабирование + мультирегион + микросервисы.
- Декомпозиция по Strangler Fig, без Big Bang.
- НФТ зафиксированы в ADR-001.

## Требования

1. Определить полный список целевых сервисов с чёткими доменными границами.
2. Обеспечить, чтобы каждый сервис соответствовал отдельной продуктовой команде.
3. Не выдумывать новые домены, которых нет в бизнес-требованиях.
4. Выделить платформенные сервисы и инфраструктурные компоненты.
5. Подготовить основу для C2 To-Be.

## Решение

### 1. Принципы выделения сервисов

- **Database per Service** — каждый сервис владеет своей БД, чужие БД напрямую
  не читает.
- **Bounded context по DDD** — границы сервисов совпадают с границами
  доменных моделей, а не с текущей оргструктурой.
- **Единая ответственность** — сервис отвечает за одну бизнес-возможность.
- **Команда = сервис** — сервис сопровождается одной командой (you build it,
  you run it).
- **Sync vs Async** — синхронные вызовы только там, где нужен немедленный
  ответ (запрос цены, бронирование); остальное — через Kafka.

### 2. Бизнес-сервисы (10)

| #  | Сервис | Bounded context                                                                                                           | Ключевые данные | Хранилище |
|----|--------|---------------------------------------------------------------------------------------------------------------------------|-----------------|-----------|
| 1  | Booking | Жизненный цикл поездки: создание, назначение, отмена, завершение                                                          | bookings, trip_state | PostgreSQL |
| 2  | Driver Profile | Онбординг водителя, документы, аккаунт, рейтинг                                                                           | drivers, documents | PostgreSQL |
| 3  | Driver Status | Онлайн-статус, геопозиция, занятость; подписан на события Booking                                                         | location, status, availability | Redis + PostGIS |
| 4  | Pricing | Тарифы, динамическое ценообразование с использованием ML-модели прогнозирования спроса (модель обучается в Data Platform) | tariffs, price_rules | PostgreSQL + Redis |
| 5  | Payments | Приём платежей от пассажира, интеграция с Яндекс Пэй                                                                      | payments, transactions | PostgreSQL |
| 6  | Payouts | Выплаты водителям, работа с банковским API                                                                                | payouts, balances | PostgreSQL |
| 7  | Notification | Push/SMS/email, шаблоны, настройки                                                                                        | notifications, templates | PostgreSQL |
| 8  | Geography | Геопоиск, маршруты, зоны, интеграция с Яндекс Картами                                                                     | zones, routes, geodata | PostGIS / Elasticsearch |
| 9  | Analytics | Операционная аналитика, BI-отчёты                                                                                         | metrics, reports | PostgreSQL |
| 10 | Fraud | Скоринг транзакций, ML-модели детекции мошенничества (обучение в Data Platform, inference внутри Fraud)                   | fraud_rules, scores | PostgreSQL |

**Обоснование разбиения Driver на два сервиса:**

Driver Profile и Driver Status имеют разные:
- **Жизненные циклы:** профиль меняется редко (регистрация, документы),
  статус — каждые несколько секунд (геопозиция, занятость).
- **Паттерны доступа:** профиль читается при онбординге и из админки;
  статус читается очень часто при матчинге заказов.
- **Хранилища:** профиль — реляционный PostgreSQL; статус — Redis
  (hot cache) + PostGIS (гео).
- **Нагрузки:** статус — высоконагруженный (location updates от 200k+
  водителей), профиль — низконагруженный.
- **Команды:** по логике это две разные компетенции (KYC/онбординг vs
  real-time matching).

### 3. BFF-слой (4)

| # | BFF | Для кого | Ответственность |
|---|-----|----------|-----------------|
| 1 | BFF Passenger | Пассажирское мобильное приложение | Агрегация данных для пассажира |
| 2 | BFF Driver | Водительское мобильное приложение | Агрегация данных для водителя |
| 3 | BFF Corporate | Корпоративный веб-портал | Отчёты, управление счетами |
| 4 | BFF Admin | Админ-панель | Управление тенантами, выплатами, fraud |

**Обоснование:** клиенты принципиально разные (мобильные vs web, разные
сценарии, разный темп изменений). 4 BFF дают независимую эволюцию клиентов
и изоляцию изменений. 

Изначально 4 BFF. В C2 Final State добавлен BFF Web для публичного веб-фронтенда.
BFF Web появляется в конце миграции (после удаления ACL), когда веб-фронтенд
переключается с прямого v2 API на собственный BFF.

### 4. Платформенные сервисы (2)

| # | Сервис | Ответственность |
|---|--------|-----------------|
| 1 | Identity/Auth | Аутентификация, авторизация, выдача токенов |
| 2 | Tenant Management | Управление партнёрами/тенантами, их конфигурация |

Identity/Auth — платформенная capability, реализуется двумя компонентами: Keycloak (OIDC-провайдер, инфраструктура) и Identity Service (управление пользователями/ролями, adapter к Keycloak).

Выделены в отдельный boundary `Platform Services`.

### 5. Инфраструктурные компоненты

| Компонент | Технология | Ответственность |
|-----------|-----------|-----------------|
| API Gateway | Kong | North-south трафик, routing, rate limiting, auth offload |
| Event Bus | Apache Kafka | Асинхронная шина доменных событий |
| Feature Flags | Unleash / LaunchDarkly | Управление фича-флагами, canary, kill switch |
| CI/CD | GitLab CI | Сборка, тесты, деплой |
| Container Registry | Docker Registry | Хранение образов |
| Observability | Prometheus, Grafana, Loki, OTel Collector, Alertmanager | Метрики, логи, трейсы, алерты |
| Data Platform / ML | Spark/Flink, ClickHouse, MLflow/Kubeflow, DataLens | Тяжёлая аналитика и ML |

### 6. C2 To-Be

C2 Final State — целевое состояние после миграции. См. C2_FinalState.puml

### 7. Что НЕ входит в это решение

- Детальный дизайн Kafka (топики, партиционирование, consumer groups) —
  предмет отдельного решения.
- Service Mesh (Istio/Linkerd) — отложено; для 12 сервисов достаточно
  библиотечных решений (tenacity, pybreaker) и Kong.
- Multi-region deployment — предмет отдельного решения.
- IAM/SSO детали — предмет отдельного решения.
- Multi-tenancy изоляция данных — предмет отдельного решения.
- Data pipeline и ML — предмет отдельного решения.

## Альтернативы

1. **Оставить 9 доменов без дробления Driver.** Отклонено: разные нагрузки,
   разные хранилища, разные жизненные циклы → отдельные сервисы.
2. **Один общий BFF на всех клиентов.** Отклонено: клиенты эволюционируют
   с разной скоростью, общий BFF создаст связанность.
3. **Service Mesh (Istio) сразу.** Отклонено: 12 сервисов — недостаточный
   масштаб для оправдания операционной сложности Istio. Отложено.
4. **Сразу выделить Rating/Review и Support.** Отклонено: этих доменов нет
   в бизнес-требованиях, не выдумываем.
5. **Модульный монолит вместо микросервисов.** Отклонено: не решает
   time-to-market ≤ 2 недель и независимый деплой.
6. **Big Bang переписывание.** Отклонено: риск длительного простоя.

## Компромиссы

- **12 сервисов** — управляемая сложность, но растёт операционная нагрузка.
  Митигация: единый Observability-стек, CI/CD-шаблоны, platform team.
- **4 BFF** — дублирование кода агрегации. Митигация: shared-библиотеки для
  общих паттернов (auth, error handling).
- **Database per Service** — усложняет кросс-доменные запросы. Митигация:
  события через Kafka + eventual consistency для не-критичных данных.
- **Без Service Mesh** — mTLS и resilience-паттерны реализуются
  библиотечно. Митигация: стандартизированные middleware в Python,
  возможная миграция на Istio при росте до 30+ сервисов.
- **Event Bus как зависимость** — если Kafka недоступна, страдает
  асинхронная коммуникация. Митигация: детальный дизайн отказоустойчивости
  в отдельном решении.
- **Sync vs Async границы** — не все границы очевидны сразу. Митигация:
  итеративное уточнение в ADR-003 и ADR-004.
