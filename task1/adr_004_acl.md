# ADR-004: Механизмы обеспечения обратной совместимости

## Контекст

Переход выполняется по Strangler Fig (ADR-003). Монолит и новые сервисы
сосуществуют весь период миграции (~12 месяцев). Клиенты (мобильные
приложения, корпоративный портал) не должны замечать переход.

Монолит сейчас использует:
- Session-based / DRF Token аутентификацию (v1).
- Celery + RabbitMQ для async (Notification, Payouts, Analytics).
- Прямые ORM-вызовы между доменами внутри монолита (sync).
- Единую PostgreSQL для всех доменов.

Нужно обеспечить:
1. Работу старых клиентов без изменений.
2. Возможность новых клиентов (OIDC) работать параллельно.
3. Постепенную замену sync-вызовов внутри монолита на вызовы новых сервисов.
4. Гарантированную доставку событий (at-least-once).
5. Возможность отката на любом шаге.

## Требования

1. Описать механизм обратной совместимости.
2. Отразить его на диаграмме C2 To-Be.
3. Обеспечить поэтапную эволюцию без простоя.

## Решение

### 1. Anti-Corruption Layer (ACL) в монолите

ACL — изолированный слой внутри монолита (Django app `acl/`). Отвечает за:

- **Routing / Dispatcher** — решает, куда отправить запрос: в legacy-логику
  монолита или в новый сервис (по feature flag).
- **v2 Controllers** — новый контроллерный слой для клиентов с OIDC.
- **Model Translators** — трансляция моделей монолита ↔ DTO сервисов.
- **HTTP Clients** — вызовы новых сервисов через REST (sync, когда нужен
  немедленный ответ: Pricing, Geography, Booking-validate).
- **Kafka Producer** — публикация событий (async) через outbox.
- **OIDC Middleware** — валидация JWT от Keycloak для v2-запросов.

**Ключевые принципы ACL:**
- **Никакой бизнес-логики.** Только трансляция, маршрутизация, публикация.
- **Однонаправленный поток:** legacy-логика → ACL → сервис/событие.
  Обратный поток — только через события от сервисов (если нужно).
- **Временный компонент.** Удаляется после полной миграции клиентов на v2
  и выноса всех доменов из монолита.

### 2. Маршрутизация v1/v2 через Kong

Вся маршрутизация — на уровне Kong (ADR-003 решение №2):

| Маршрут | Куда | Auth | Клиенты |
|---------|------|------|---------|
| `/api/v1/*` | Monolith Legacy API | Session / DRF Token | Старые мобильные приложения, корпоративный портал |
| `/api/v2/*` | Monolith ACL | OIDC (Keycloak JWT) | Новый веб-фронтенд, BFF новых мобильных клиентов |
| `/api/bff/*` | BFF-сервисы | OIDC | Новые мобильные приложения (постепенно) |

**Логика:** v1 и v2 — не версии API, а пути для разных клиентов. Старые
клиенты не меняются, новые идут через ACL/BFF.

### 3. Транзакционный Outbox

Для гарантированной публикации событий в Kafka из монолита:

1. Бизнес-транзакция пишет изменения в БД монолита **и** в таблицу `outbox`
   в одной транзакции.
2. Отдельный poller (часть `app_worker`) читает `outbox` и публикует в Kafka.
3. После успешной публикации — помечает запись как `published`.

**Свойства:**
- At-least-once delivery (дубли возможны, consumer'ы идемпотентны).
- Никаких потерь событий при падении монолита.
- Порядок событий — по `created_at` в outbox (per aggregate).

### 4. Kafka в монолите: только Producer

**Монолит — только producer.** Consumers — в новых сервисах. Исключение:
ACL может содержать consumer'ы **только** для тех событий, которые нужны
legacy-логике монолита (например, `DriverStatusChanged` для Booking,
если Booking ещё в монолите). Такие consumer'ы временные и удаляются
вместе с соответствующим доменом.

### 5. Эволюция ACL по волнам (синхронизация с ADR-003)

| Волна | Что делает ACL |
|-------|----------------|
| 0 | Создаётся каркас: routing v1/v2, OIDC middleware, outbox, HTTP clients |
| 1 | v1 Notification → Kafka (outbox). Consumer'ов в монолите нет (Notification только публикует) |
| 2 | v1 Tenant, Geography, Driver Profile → HTTP через ACL. Translator'ы для трёх сервисов |
| 3 | v1 Pricing → HTTP через ACL. Shadow mode для сравнения расчётов |
| 4 | v1 Driver Status → Kafka (outbox) для location updates, HTTP для запросов статуса |
| 5 | v1 Payments, Payouts → HTTP через ACL. Dual-write на время перехода |
| 6 | v1 Booking → HTTP через ACL. Старые поездки — монолит, новые — сервис (по feature flag) |
| Финал | Монолит содержит только legacy-код для v1. ACL — тонкий слой маршрутизации |

### 6. Feature Flags

Управление переключением v1/v2 и shadow/dual режимами:

- **LaunchDarkly / Unleash / собственный сервис** — выбор по масштабу.
- Ключевые флаги:
    - `notification.via_kafka` — источник Notification (Celery vs Kafka).
    - `pricing.shadow_mode` — параллельный расчёт.
    - `payments.dual_write` — dual-write платежей.
    - `booking.routing` — процент трафика на новый Booking.
- **Kill switch:** мгновенный откат на legacy-путь.

## Альтернативы

1. **BFF-only без ACL в монолите.** Отклонено: BFF покрывает только новых
   клиентов, а старым клиентам всё равно нужен путь в монолит. ACL решает
   именно эту задачу.
2. **Dual-write без outbox.** Отклонено: риск потери событий при падении
   между записью в БД и публикацией в Kafka.
3. **Service Mesh (Istio) для resiliency.** Отклонено: 12 сервисов —
   недостаточный масштаб, операционная сложность не оправдана.
   Библиотечные решения (tenacity, pybreaker) достаточны.
4. **Прямой Kafka producer без outbox.** Отклонено: at-most-once delivery,
   риск потери событий.
5. **Big Bang роутинг.** Отклонено: нет обратной совместимости, огромный
   blast radius.

## Компромиссы

- **ACL — долгоживущий компонент** (весь год миграции). Требует владельца,
  документации, тестов. Митигация: строгая граница ответственности
  (никакой бизнес-логики).
- **Монолит меняется** (появляется ACL, outbox, OIDC middleware). Это не
  «чистая» обратная совместимость, а **аддитивная**: старые пути
  не ломаются, новые добавляются. Митигация: feature flags, canary-rollout.
- **Outbox добавляет нагрузку на БД** (доп. таблица, poller). Митигация:
  outbox — append-only, очищается после публикации.
- **Два API (v1 и v2) в монолите** — нужно поддерживать оба. Митигация:
  v1 — только критичные фиксы, вся новая функциональность — только в v2
  и/или в сервисах.
- **v1/v2 routing в Kong** — единая точка управления, но добавляет hop.
  Митигация: Kong — стандартный, проверенный компонент.
- **Тестирование ACL** — интеграционные тесты, contract tests против
  сервисов, shadow mode. Митигация: непрерывное тестирование в рамках
  производственного pipeline (не отдельный проект).
