# ADR-005: План миграции данных

## Контекст

Переход на микросервисы выполняется по Strangler Fig (ADR-003) с ACL
(ADR-004). Каждый сервис получает свою БД (Database per Service), данные
из монолитной PostgreSQL должны быть перенесены без потерь и без
существенного простоя.

Текущее состояние:
- Единая PostgreSQL (~10–20 ТБ) со всеми доменными данными.
- ClickHouse для аналитики (~100–200 ТБ).
- Redis для кеша (device tokens, сессии, временные данные).
- Elasticsearch для геопоиска.
- Активная нагрузка: 200 000 конкурентных поездок, 100 000 RPS на пике.

Ограничения:
- Простой критических сервисов недопустим (Booking, Payments, Payouts).
- Для не-критичных сервисов допустимо короткое окно (5–15 мин).
- Данные должны быть консистентны на момент cutover.
- Возможность отката на любом этапе.

## Требования

1. Описать общий паттерн миграции данных.
2. Указать инструменты.
3. Для каждого сервиса — конкретный план миграции с окном cutover.
4. Описать механизмы verification и reconciliation.
5. Описать rollback-стратегию.
6. Зафиксировать рабочие оценки объёмов данных.
7. Указать, что НЕ входит в это решение.

## Решение

### 1. Общий паттерн миграции (6 шагов)

Применяется для всех stateful сервисов с вариациями:

| Шаг | Что делаем | Простой? |
|-----|-----------|----------|
| 1. **Pre-copy (batch backfill)** | Начальный перенос исторических данных из `db_main` в БД сервиса. Работает без остановки записи в монолит | Нет |
| 2. **CDC (Debezium)** | Включаем CDC: все изменения из `db_main` реплицируются в новую БД в реальном времени | Нет |
| 3. **Dual-write** | На время перехода монолит пишет в обе БД (свою и сервиса). Сервис — source of truth для новых записей | Нет |
| 4. **Verification** | Автоматическая сверка данных между `db_main` и БД сервиса (count, checksums, business invariants) | Нет |
| 5. **Cutover** | Переключение трафика на сервис. Монолит → read-only для этого домена | Зависит от сервиса |
| 6. **Cleanup** | Удаление legacy-таблиц монолита после стабилизации (≥ 30 дней) | Нет |

**Вариации:**
- **Notification, Analytics** — без dual-write (только CDC + cutover), потому что данные append-only.
- **Driver Status** — история не мигрируется, только активные водители (volatile данные в Redis+PostGIS).
- **Booking, Payments, Payouts** — строгий режим: reconciliation + гарантированный rollback.
- **Geography** — миграция справочников (зоны, маршруты), меняются редко → pre-copy + короткий cutover.

### 2. Инструменты

| Инструмент | Роль |
|------------|------|
| **Debezium** | CDC из PostgreSQL (`db_main`) → Kafka → сервисные БД |
| **Kafka Connect** | Оркестрация коннекторов Debezium |
| **Custom backfill jobs** | Python-скрипты для pre-copy (батчами, с throttling) |
| **reconciliation-framework** | Внутренняя библиотека: сверка count/checksums/invariants между БД |
| **Flyway / Alembic** | Миграции схемы сервисных БД |
| **Feature Flags (Unleash)** | Управление переключением и shadow mode (ADR-004) |

### 3. Окна cutover по сервисам

| Категория | Сервисы | Допустимый простой |
|-----------|---------|-------------------|
| **Zero-downtime** | Booking, Payments, Payouts, Pricing | 0 (cutover через feature flag + dual-write) |
| **Короткое окно (5–15 мин)** | Notification, Analytics, Geography | 5–15 мин (приемлемо) |
| **Короткое окно + freeze** | Driver Profile, Tenant Management, Identity | 5–15 мин (off-peak) |
| **Без простоя (volatile)** | Driver Status | 0 (новая БД заполняется из активных данных) |
| **Без простоя (append-only)** | Fraud | 0 (CDC + shadow) |

### 4. Per-service план миграции

#### 4.1 Booking (PostgreSQL ~5 ТБ)

| Шаг | Детали |
|-----|--------|
| Pre-copy | Батчами по 100k строк, приоритет — активные поездки (последние 90 дней), затем история |
| CDC | Debezium на таблицы `bookings`, `trip_state` |
| Dual-write | Через ACL (ADR-004): новые поездки пишутся в `svc_booking` + `db_main`. Старые читаются из монолита |
| Cutover | По feature flag `booking.routing_percent`: 1 → 10 → 50 → 100% **новых** поездок |
| Verification | Reconciliation: количество поездок, суммы, статусы по каждому дню |
| Rollback | Feature flag → 0%, возврат на монолит. ≤ 5 мин |
| Простой | 0 |

#### 4.2 Driver Profile (PostgreSQL ~1 ТБ)

| Шаг | Детали |
|-----|--------|
| Pre-copy | Полный backfill (данные меняются редко) |
| CDC | Debezium на `drivers`, `documents` |
| Dual-write | Через ACL: обновления профиля пишутся в обе БД |
| Cutover | Off-peak окно (ночь), 5–10 мин |
| Verification | Reconciliation: количество водителей, документов, статусов верификации |
| Rollback | Возврат на монолит, ≤ 15 мин |
| Простой | 5–10 мин |

#### 4.3 Driver Status (Redis + PostGIS — volatile)

| Шаг | Детали |
|-----|--------|
| Pre-copy | **Нет** — история не нужна |
| Заполнение | Активные водители: их текущий статус, геопозиция, занятость |
| CDC + Dual-write | Location updates через Kafka (ADR-004) — параллельно в `db_main` и `svc_driver_status` |
| Cutover | Feature flag `driver_status.location_via_kafka` |
| Verification | Сравнение позиций активных водителей (расхождение ≤ 50 м) |
| Rollback | Feature flag, ≤ 5 мин |
| Простой | 0 |

#### 4.4 Pricing (PostgreSQL + Redis ~200 ГБ)

| Шаг | Детали |
|-----|--------|
| Pre-copy | Тарифы, правила — полный backfill |
| CDC + Dual-write | Shadow mode через ACL (ADR-004): параллельно старый и новый расчёт |
| Cutover | После 7 дней без расхождений → `pricing.use_new=true` |
| Verification | Сравнение результатов расчёта (shadow mode) |
| Rollback | Feature flag, ≤ 5 мин |
| Простой | 0 |

#### 4.5 Payments (PostgreSQL ~3 ТБ)

| Шаг | Детали |
|-----|--------|
| Pre-copy | Батчами, с приоритетом активных транзакций |
| CDC | Debezium на `payments`, `transactions` |
| Dual-write | **Строгий режим**: транзакции пишутся в обе БД + reconciliation job |
| Cutover | Постепенный rollout: 1 → 10 → 50 → 100% |
| Verification | Reconciliation: суммы, статусы, комиссии, сверка с Яндекс Пэй |
| Rollback | Feature flag, ≤ 15 мин. При расхождениях — автоматический алерт |
| Простой | 0 |

#### 4.6 Payouts (PostgreSQL ~2 ТБ)

| Шаг | Детали |
|-----|--------|
| Pre-copy | Батчами, приоритет активных балансов |
| CDC | Debezium на `payouts`, `balances` |
| Dual-write | Строгий режим + reconciliation по балансам |
| Cutover | Постепенный rollout |
| Verification | Reconciliation балансов, история выплат, сверка с банковским API |
| Rollback | Feature flag, ≤ 15 мин |
| Простой | 0 |

#### 4.7 Notification (PostgreSQL ~500 ГБ)

| Шаг | Детали |
|-----|--------|
| Pre-copy | Шаблоны, preferences — полный backfill. История уведомлений — только последние 90 дней |
| CDC | **Без dual-write** — только CDC: монолит продолжает писать, ACL перехватывает и публикует в Kafka |
| Cutover | Feature flag `notification.via_kafka=true` → Celery отключается |
| Verification | Сравнение количества уведомлений (Celery vs Kafka) за 7 дней |
| Rollback | Feature flag, ≤ 5 мин |
| Простой | 0 (короткое окно 5 мин при переключении) |

#### 4.8 Geography (PostGIS / Elasticsearch ~300 ГБ)

| Шаг | Детали |
|-----|--------|
| Pre-copy | Зоны, маршруты, геоиндексы — полный backfill |
| CDC + Dual-write | Обновления зон пишутся в обе БД |
| Cutover | Off-peak окно 10 мин |
| Verification | Сравнение результатов геопоиска и маршрутов (shadow mode) |
| Rollback | Возврат на монолит, ≤ 15 мин |
| Простой | 10 мин |

#### 4.9 Analytics (PostgreSQL → Data Platform, гибридный подход)

| Шаг | Детали |
|-----|--------|
| Pre-copy | **Миграция последних 6–12 месяцев** истории в Data Platform (ClickHouse) |
| Архив | Старые данные (> 12 месяцев) — остаются в старой аналитике, доступны только для чтения |
| CDC | Async через Kafka: `svc_analytics` подписан на все доменные события |
| Dual-read | Отчёты читаются из нового сервиса, fallback — старая аналитика |
| Cutover | Feature flag `analytics.use_service` |
| Verification | Сравнение отчётов (count, суммы, топ-N) за последние 30 дней |
| Rollback | Feature flag, ≤ 30 мин (потому что объём) |
| Простой | 15 мин на cutover |

**Обоснование гибрида:** полная миграция 100+ ТБ дорога по времени (дни/недели) и не даёт бизнес-ценности. Старые данные остаются доступны через архив.

#### 4.10 Fraud (PostgreSQL ~1 ТБ)

| Шаг | Детали |
|-----|--------|
| Pre-copy | Правила, скоры, история срабатываний |
| CDC + Shadow | `svc_fraud` получает те же события, что монолит, но работает в shadow mode |
| Cutover | После 7 дней без расхождений → `fraud.use_service=true` |
| Verification | Сравнение fraud-скоров (shadow mode) |
| Rollback | Feature flag, ≤ 5 мин |
| Простой | 0 |

#### 4.11 Identity/Auth (PostgreSQL ~100 ГБ)

| Шаг | Детали |
|-----|--------|
| Pre-copy | Пользователи, роли, сессии (только активные сессии) |
| Миграция | Keycloak импортирует пользователей через Admin API / LDAP |
| Cutover | Off-peak, 10 мин |
| Verification | Сравнение пользователей, ролей, успешных логинов |
| Rollback | Возврат на Django auth, ≤ 15 мин |
| Простой | 10 мин |

#### 4.12 Tenant Management (PostgreSQL ~50 ГБ)

| Шаг | Детали |
|-----|--------|
| Pre-copy | Полный backfill (данные компактные) |
| CDC | Debezium |
| Cutover | Off-peak, 5 мин |
| Verification | Reconciliation: количество тенантов, конфигурации |
| Rollback | ≤ 5 мин |
| Простой | 5 мин |

### 5. Verification & Reconciliation

**Уровни проверки:**

| Уровень | Что проверяем | Инструмент |
|---------|---------------|-----------|
| **Row count** | Количество строк по таблицам | reconciliation-framework |
| **Checksums** | Контрольные суммы по ключевым полям (суммы платежей, балансы) | reconciliation-framework |
| **Business invariants** | Инварианты (например, `sum(payments) = sum(payouts) + commissions`) | Custom SQL |
| **Shadow mode** | Сравнение результатов расчёта (Pricing, Fraud) | ACL (ADR-004) |
| **Sampling** | Выборочная сверка 1% записей по бизнес-сценариям | reconciliation-framework |

**Периодичность:**
- **До cutover:** сверка ежедневно, расхождения → блокировка cutover.
- **На cutover:** полная сверка, go/no-go.
- **После cutover (30 дней):** сверка ежедневно, алерты на расхождения.

### 6. Rollback стратегия

**Уровни отката:**

| Уровень | Когда применяем | Действие | Время |
|---------|-----------------|----------|-------|
| **Traffic rollback** | Расхождения после cutover | Feature flag → возврат на монолит | ≤ 5 мин |
| **Data rollback** | Потеря данных при dual-write | Восстановление из snapshot БД сервиса + replay из outbox | ≤ 1 час |
| **Schema rollback** | Ошибка миграции схемы | Alembic downgrade | ≤ 30 мин |
| **Full rollback** | Критическая ошибка | Возврат всего домена на монолит, сервис → offline | ≤ 1 час |

**Ключевое:** монолит остаётся source of truth до 100% cutover + 30 дней стабильной работы. Legacy-таблицы удаляются только после этого.

### 7. Рабочие оценки объёмов данных

> **Assumption:** в кейсе цифр нет. Это рабочие оценки для планирования миграции, не требования.

| Источник | Оценка | Обоснование |
|----------|--------|-------------|
| PostgreSQL (основная БД) | ~10–20 ТБ | 200k поездок × история, все домены |
| ClickHouse (аналитика) | ~100–200 ТБ | События, метрики, агрегаты |
| Booking DB | ~5 ТБ | История поездок |
| Payments DB | ~3 ТБ | Транзакции, история |
| Payouts DB | ~2 ТБ | Выплаты, балансы |
| Driver Profile DB | ~1 ТБ | Документы, история |
| Fraud DB | ~1 ТБ | Скоры, правила, история |
| Notification DB | ~500 ГБ | История уведомлений (последние 90 дней) |
| Geography Store | ~300 ГБ | Зоны, маршруты, индексы |
| Pricing Store | ~200 ГБ | Тарифы, правила, кеш |
| Identity DB | ~100 ГБ | Пользователи, сессии |
| Tenant DB | ~50 ГБ | Тенанты, конфигурация |

**Суммарно:** ~15–30 ТБ операционных данных + 100–200 ТБ аналитики.

### 8. Что НЕ входит в это решение

- Инфраструктурная миграция (Kubernetes, сети, хранилища) — отдельное решение.
- Миграция данных Data Platform (Spark/Flink → ClickHouse) — предмет отдельного решения.
- Миграция ML-моделей и feature store — предмет отдельного решения.
- Multi-region replication данных — предмет отдельного решения.
- Резервное копирование и DR — отдельное решение.

## Альтернативы

1. **Big Bang миграция всех данных.** Отклонено: длительный простой, огромный blast radius.
2. **Без CDC, только batch.** Отклонено: невозможно обеспечить консистентность при активной записи.
3. **Полная миграция Analytics (100+ ТБ).** Отклонено: дорого, долго, низкая бизнес-ценность → гибрид.
4. **Миграция Driver Status с историей.** Отклонено: volatile данные, история не имеет ценности → только активные.
5. **Cutover без dual-write.** Отклонено: риск потери данных между backfill и cutover.

## Компромиссы

- **Pre-copy + CDC + dual-write** — самый дорогой по трудозатратам паттерн, но единственный безопасный при 200k активных поездок. Митигация: автоматизация через reconciliation-framework.
- **Строгий режим для Booking/Payments/Payouts** — больше времени на миграцию, но гарантия корректности. Митигация: параллельные волны для не-критичных сервисов.
- **Гибрид для Analytics** — старые данные остаются в архиве, что создаёт «две аналитики». Митигация: read-only access к старой аналитике + план полной миграции на следующий год.
- **Короткие окна простоя (5–15 мин)** для не-критичных сервисов. Митигация: off-peak время, предупреждения пользователям.
- **Оценки объёмов — assumptions** — могут быть неточны. Митигация: уточнение на этапе discovery перед каждой волной.
- **Dual-write добавляет нагрузку на БД** — на время перехода. Митигация: ограниченный период (≤ 4 недели на сервис).
