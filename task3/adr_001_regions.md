# ADR-001: Выбор регионов развёртывания

## Контекст

GoFuture переходит с Django-монолита на микросервисы (Task1) и внедряет
событийную архитектуру на Kafka (Task2). Task2 зафиксировал
мультирегиональность как **≥ 3 регионов** и использовал символьные
`region-a/b/c` — как placeholder для партиционирования топиков и `region`
в envelope событий. Task3 должен **материализовать** эти placeholder
в конкретные регионы.

Из Task1 (ADR-001) и задания:
- Целевая доступность критических сервисов — **99,99%** (зафиксировано
  в Task2, подтверждено в задании Task3).
- Горизонтальное масштабирование, несколько регионов.
- Комплаенс: соответствие локальным регуляторным требованиям.
- Явное требование задания: **пользователи в Юго-Восточной Азии и Южной
  Америке**, низкая latency.
- Явное требование задания: **более трёх географических регионов**.

Достижимость 99,99%:
- ЦОД уровня **TIER IV** (отказоустойчивый, N+1 по всем системам).
- Виртуализация ESXi + Kubernetes с резервированием подов.
- Избыточность по зонам внутри региона.
- Вторая зона (второй город, где это возможно) с репликами и
  **автоматическим failover за 45 минут**.
- RTO для критичных сервисов — **≤ 45 мин** (assumption, зафиксировано
  здесь).

## Требования

1. Покрыть целевые рынки задания: ЮВА и Южная Америка (обязательно).
2. Сохранить домашний рынок из Task1 (RU/СНГ).
3. Обеспечить низкую latency для пользователей в целевых регионах
   (p95 ≤ 100 мс для критичных операций — assumption).
4. Не менее 4 регионов (≥ 3 по Task1 + запас под MENA).
5. Каждый регион — в отдельной **регуляторной зоне** (data residency).
6. Каждый регион — **2 зоны** (зона 1 + зона 2) для DR. Для регионов,
   где второй город физически недоступен в той же регуляторной зоне, —
   **частичный DR** (только non-PII).
7. Соответствие локальным режимам (152-ФЗ, PDPA, LGPD, UAE DP).
8. Совместимость с Task2: регион — часть имени Kafka-топика
   (`<region>.<domain>.events`), `region` — в envelope.

## Решение

### 1. Выбранные регионы (4)

| Регион (код) | Зона 1 | Зона 2 (DR) | Регуляторная зона | Обоснование |
|---|---|---|---|---|
| **region-sea** | Сингапур | Батам, Индонезия (**частичный DR**) | PDPA Singapore + PDPA Indonesia | **Прямое требование задания** (ЮВА). Хаб ЮВА, минимальная latency к Индонезии/Малайзии/Таиланду/Вьетнаму. Сингапур — город-государство, второго города в SG нет. Батам (Индонезия, ~30 км) — вторая зона для non-PII. PII — только Сингапур. |
| **region-latam** | Сан-Паулу | Рио-де-Жанейро | LGPD Brazil | **Прямое требование задания** (Южная Америка). Крупнейший рынок ЮА. Два города → реальный DR в той же регуляторной зоне. |
| **region-ru** | Москва | Санкт-Петербург | 152-ФЗ (data residency) | Домашний рынок из Task1: ядро бизнеса, корп-клиенты, история. Два города → реальный DR в той же регуляторной зоне. |
| **region-mena** | Дубай | Абу-Даби | UAE DP Law + DIFC | Комплементарен по часовым поясам (закрывает EU/Африку/Ближний Восток). Растущий рынок. Два города в ОАЭ → реальный DR в той же регуляторной зоне. |

### 2. Обоснование выбора (по критериям)

| Критерий | Как влияет на выбор |
|---|---|
| **Покрытие задания** | SEA и LatAm — обязательны по тексту задания. Не выбор, а требование. |
| **Домашний рынок** | RU — из Task1, здесь ядро. Отказ от RU = потеря существующего бизнеса. |
| **Часовые пояса** | 4 региона покрывают 24 часа: SEA (UTC+8), LatAm (UTC−3), RU (UTC+3), MENA (UTC+4). Follow-the-sun поддержка без ночных смен. |
| **Регуляторное разнообразие** | 4 разных режима (PDPA, LGPD, 152-ФЗ, UAE DP) → содержательная compliance-стратегия (ADR-005). |
| **Платёжные экосистемы** | Каждый регион — своя платёжная экосистема (см. ADR-005). RU-эквайринг в SEA не работает. |
| **Картография** | Yandex Maps — только RU. В SEA/LatAm/MENA — локальные провайдеры (см. ADR-005). |
| **TIER IV ЦОД** | Все 4 региона — TIER IV в зоне 1. Все 4 региона имеют вторую зону (для SEA — частичный DR). |

### 3. Регуляторные зоны (фундамент для ADR-002 и ADR-005)

| Регуляторная зона | Регион | Что можно реплицировать за пределы зоны |
|---|---|---|
| **RU** | region-ru | Ничего с PII. Только агрегаты аналитики (хэшированные). |
| **SEA** | region-sea | Ничего с PII. Только агрегаты. **Внутри зоны** — только non-PII во вторую зону (Батам). |
| **LatAm** | region-latam | Ничего с PII. Только агрегаты. |
| **MENA** | region-mena | Ничего с PII. Только агрегаты. |

**Cross-border репликации PII между зонами нет.** Обмен между зонами —
только через API (pull-on-consent) для роуминга пользователей
(дизайн в ADR-003).

### 4. Две зоны на регион — модель DR

| Регион | Модель | Обоснование |
|---|---|---|
| region-ru | **2 города** (Москва → СПб) | Потеря города = failover в СПб за ≤ 45 мин (RTO). Репликация async, RPO ≤ 15 мин для финансов, ≤ 1 ч для остальных (assumption, уточняется в ADR-002). |
| region-latam | **2 города** (Сан-Паулу → Рио) | Аналогично RU. |
| region-mena | **2 города** (Дубай → Абу-Даби) | ОАЭ — не город-государство, два крупных города в одной регуляторной зоне (UAE DP Law). Реальный DR как у RU/LatAm. Репликация async, RPO ≤ 15 мин для финансов, ≤ 1 ч для остальных. |
| region-sea | **Сингапур (зона 1) + Батам (зона 2, частичный DR)** | Сингапур — город-государство, второго города в SG нет. Батам (Индонезия, ~30 км) — вторая зона **только для non-PII**: outbox, агрегаты аналитики, конфиги, схемы, ML-модели, резервные образы. **PII (транзакции, KYC, device tokens) — только в Сингапуре**, cross-border запрещён (PDPA SG + PDPA ID). При потере Сингапура: восстановление non-PII из Батама, PII — из бэкапов в Сингапуре (потеря = принятый риск). |

**RTO:** ≤ 45 мин для критичных (Booking, Payments, Pricing, Identity,
Driver Profile, Driver Status), ≤ 4 ч для не-критичных.
**RPO:** ≤ 15 мин для финансов (Payments, Payouts), ≤ 1 ч для остальных.
Для SEA-PII RPO фактически = ∞ (потеря Сингапура = потеря SEA-PII).

### 5. Арифметика Task2 → Task3 (3 региона → 4)

Task2 ADR-002 зафиксировал **3 placeholder-региона** (`region-a/b/c`).
Task3 материализует **4**:

| Параметр | Task2 (placeholder 3) | Task3 (материализовано 4) |
|---|---|---|
| Типов топиков на регион | 9 | 9 |
| events-топиков | 9 × 3 = 27 | 9 × 4 = **36** |
| DLQ-топиков | 9 × 3 = 27 | 9 × 4 = **36** |
| retry-топиков (1/5/15 мин) | 27 × 3 = 81 | 36 × 3 = **108** |
| **Итого топиков** | **135** | **180** |

**Это не ошибка Task2** — Task2 зафиксировал принцип «per-domain ×
per-region», Task3 доводит количество регионов до 4. Пересчёт счётчиков
фиксируется здесь и в README Task3.

Имена топиков: `<region>.<domain>.events`, где
`region ∈ {region-ru, region-sea, region-latam, region-mena}`.

Envelope события (Task2 ADR-001) не меняется — `region` теперь принимает
одно из 4 значений.

### 6. Что НЕ входит в это решение

- Схема репликации данных между зонами — **ADR-002**.
- Геомаршрутизация (DNS, WAF, GLB) — **ADR-003**.
- План failover и таблица сценариев — **ADR-004**.
- Комплаенс per-region (регуляторные детали) — **ADR-005**.
- Security-overlay (WAF, Firewall, DDoS) — **ADR-006**.
- Инфраструктура (TIER IV, ESXi, Kubernetes, sizing) —
  инфраструктурное решение, вне scope ADR.

## Альтернативы

1. **3 региона (SEA, LatAm, RU) без MENA.** Отклонено: задание требует
   «более трёх регионов». Три — на грани; четвёртый даёт запас и покрытие
   MENA, что закрывает часовые пояса.
2. **Добавить EU (Франкфурт) вместо MENA.** Отклонено: EU не целевой
   по заданию, GDPR добавляет регуляторной сложности без явной
   бизнес-ценности. MENA — растущий рынок + комплементарен по часовым
   поясам.
3. **Добавить Северную Америку (США).** Отклонено: не целевой по заданию;
   CCPA/CPRA + штат-специфичные законы → сложность без явной ценности.
4. **Замена RU на другую локацию.** Отклонено: RU — домашний рынок
   из Task1, потеря = отказ от существующего бизнеса.
5. **Один регион с multi-AZ.** Отклонено: не покрывает требования задания
   (SEA + LatAm + >3 регионов) и не даёт DR при потере города.
6. **Два региона (SEA + LatAm) как единственные.** Отклонено: нарушает
   Task1 (≥ 3 регионов) и задание (> 3 регионов).
7. **SEA = Сингапур + Батам как full-DR.** Отклонено: cross-border PII
   запрещён (PDPA SG + PDPA ID). Компромисс — частичный DR (non-PII).
8. **SEA = Сингапур + Джакарта как full-DR.** Отклонено по той же причине,
   что и п. 7; Джакарта дальше Батама без выигрыша по residency.

## Компромиссы

- **SEA — частичный DR.** Второго города в Сингапуре нет. Батам
  (Индонезия) — вторая зона только для **non-PII** (outbox, агрегаты,
  конфиги, схемы, ML-модели, образы). PII — только Сингапур. **Потеря
  Сингапура целиком = потеря SEA-PII** (принятый риск, страховка —
  бэкапы в том же регионе). Митигация для non-PII: восстановление
  из Батама за ≤ 4 ч. Альтернатива (Батам как full-DR) отвергнута:
  cross-border PII запрещён (PDPA SG + PDPA ID).
- **MENA — реальный DR (Дубай + Абу-Даби).** Ранее в таблице ошибочно
  стояло «multi-AZ»; ОАЭ — не город-государство, два города в одной
  регуляторной зоне → полноценный DR как у RU/LatAm.
- **4 региона вместо 3 → +45 Kafka-топиков** (135 → 180). Митигация:
  GitOps (Terraform + Kafka operator, зафиксировано в Task2 ADR-002),
  автоматизация создания.
- **RTO 45 мин — assumption.** Достижим только при автоматическом
  failover (health checks + orchestrator). Ручной failover = 2–4 ч.
  Автоматика — в ADR-004.
- **RPO 15 мин / 1 ч — assumption.** Более строгий RPO (секунды)
  требует sync-репликации → неприемлемая latency для записи. Async —
  компромисс.
- **99,99% в SEA — только для AZ-катастроф.** Потеря Сингапура целиком —
  риск выше целевого (PII не восстановить из Батама). Фиксируем как
  принятый риск. **MENA: 99,99% достижим полностью** (Дубай → Абу-Даби
  за ≤ 45 мин).
- **Часовые пояса ≠ покрытие языков/культур.** Каждый регион —
  локализация (язык, формат, платёжные привычки). Не в scope Task3,
  но влияет на TTM (Task1 ADR-001).
