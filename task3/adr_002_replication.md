# ADR-002: Схема репликации данных между регионами

## Контекст

ADR-001 материализовал 4 региона (`region-ru`, `region-sea`, `region-latam`,
`region-mena`), каждый в своей регуляторной зоне, с двумя зонами на регион
(для SEA — частичный DR). Задание Task3 требует «схему репликации данных
между регионами».

Уже зафиксировано:
- Task2 ADR-002: Kafka MirrorMaker **не используется**. Каждый регион —
  изолированный кластер. Обмен между регионами — через API.
- Task1 ADR-001: 99,99% доступности, RTO/RPO — assumption (Task3).
- Task2 ADR-001: `region` в envelope событий.
- ADR-001 Task3: 4 региона, регуляторные зоны, RTO ≤ 45 мин, RPO ≤ 15 мин
  (финансы) / ≤ 1 ч (остальные).

**Ключевой принцип:** «реплицировать» ≠ «копировать всё». Из-за data
residency большая часть бизнес-данных **не покидает** свой регион.
Репликация делится на 5 корзин — 4 «что реплицируем» + 1 «что осознанно
не реплицируем».

## Требования

1. Обеспечить RTO ≤ 45 мин и RPO ≤ 15 мин (финансы) / ≤ 1 ч (остальные)
   для критичных сервисов.
2. Не нарушать data residency (PII — только в своей регуляторной зоне).
3. Обеспечить единое состояние control-plane (схемы, флаги, правила,
   конфиги, secrets) во всех регионах.
4. Обеспечить глобальную аналитику (non-PII агрегаты).
5. Не дублировать Task2 ADR-002 (Kafka-топики, отказ от MirrorMaker).
6. Отразить размещение Global Control Plane и Global Analytics.

## Решение

### 1. Пять корзин репликации

#### Корзина 1. Global Control Plane — синхронизируется везде

| Что | Зачем реплицировать | Почему нельзя только локально |
|---|---|---|
| **Apicurio schemas** (Avro, 20 событий) | Продюсер и консьюмер в разных регионах должны понимать один контракт | Дрейф схем = битые события |
| **Feature flags** (Unleash) | Canary / kill-switch синхронно во всех регионах | Локальный флаг = регион по другой логике |
| **Fraud rules** (сами правила, не скоры) | Fraud-кольца跨региональные, правила — глобальный ассет | Обход через регион |
| **Tenant configs** (корп-клиенты, квоты, лимиты) | Корп-клиент с офисами в 4 регионах — один договор | Рассинхрон = нарушение SLA |
| **Global Identity Directory** (`user_id → home_region`, без PII) | Роутинг путешественников | Некуда слать API-запрос при роуминге |
| **Secrets / keys** (Vault) | Одинаковые ключи JWT / шифрования | Невозможно валидировать токены cross-region |

**Механизм:** GitOps + pull-on-start + webhook. **Kafka-репликация
не используется** (MirrorMaker отвергнут в Task2 ADR-002). Синк через
API-пулл / config-service.

#### Корзина 2. Global reference data — read-only, редко меняется

| Что | Зачем |
|---|---|
| **Pricing base catalog** (тарифы, surge multipliers) | Глобальный каталог + региональный overlay |
| **ML model artifacts** (MLflow → S3 per region) | Модели обучаются глобально, сервятся везде |
| **Push/SMS/email шаблоны** | Глобальный каталог, локализация per-region — overlay |
| **Geography base** (дорожный граф, базовые границы) | Медленно меняется, дорого тянуть каждый раз |

**Механизм:** nightly sync + on-new-version. Только read-only.

#### Корзина 3. Cross-region business data — только агрегаты

| Что | Зачем | Ограничение |
|---|---|---|
| **Analytics aggregates** (regional ClickHouse → Global ClickHouse) | Глобальные отчёты, capacity planning, investor reporting | Только агрегаты, никаких PII |
| **Fraud signals** (hashed, агрегированные) | Кросс-региональные паттерны фрода | Только хэши + сигналы, не транзакции |
| **Corp consolidated billing** | Корп-клиент видит все поездки | Через API к домашним регионам, не реплика |

**Механизм:** batch export (S3) → global cluster. **Никогда online-реплика.**

#### Корзина 4. DR-реплики — внутри регуляторной зоны

| Что | Куда | Протокол | RPO |
|---|---|---|---|
| **PostgreSQL** (Booking, Payments, Payouts, Driver Profile, Driver Status, Identity, Tenant) | Вторая зона того же региона | Streaming replication (async) | ≤ 15 мин (финансы), ≤ 1 ч (остальные) |
| **ClickHouse** (аналитика) | Вторая зона того же региона | Backup + restore в standby | ≤ 1 ч |
| **Object storage** (KYC, media) | Вторая зона того же региона | S3 cross-city replication | ≤ 15 мин |
| **Keycloak realm** | Вторая зона того же региона | Read-replica + backup | ≤ 5 мин |
| **Redis / Driver Status** | **Не реплицируем** | — | Volatile, восстанавливается из живых водителей |
| **Kafka** | **Не реплицируем cross-region** | — | MirrorMaker отвергнут (Task2 ADR-002) |

**Граница DR — только внутри одной регуляторной зоны.** RU-данные →
только RU, SEA → только SEA, LatAm → только LatAm, MENA → только MENA.

**Различие по регионам:**
- **RU / LatAm / MENA** — два города в одной регуляторной зоне → полный
  DR (PII + non-PII). RPO ≤ 15 мин / ≤ 1 ч. RTO ≤ 45 мин.
- **SEA** — Батам (Индонезия) получает **только non-PII** (outbox,
  агрегаты, конфиги, схемы, ML-модели, образы). **PII — только
  Сингапур**, cross-border запрещён (PDPA SG + PDPA ID). Потеря
  Сингапура целиком = потеря SEA-PII (принятый риск, ADR-001).

#### Корзина 5. Что НЕ реплицируем (осознанно)

| Что | Почему |
|---|---|
| **Booking transactional data** | Поездка в одном регионе; репликация = нарушение residency |
| **Payments / Payouts** | Финансовые данные — в регионе, без исключений |
| **Driver location stream** | Sub-second freshness; водитель физически в регионе |
| **Notification content / device tokens** | Per-region (языки, консенты) |
| **Outbox / processed_events / DLQ** | Операционное состояние, per-region ops |
| **Сессии (в базовом виде)** | Живут в регионе аутентификации; cross-region — через API |

**Cross-region PII не реплицируется никогда.** Роуминг пользователей —
через API-вызов к домашнему региону (дизайн в ADR-003), не через
репликацию.

### 2. Placement policy для Global-слоёв

**Проблема:** Global Control Plane и Global Analytics на диаграмме —
логические boundary. Их физическое размещение не зафиксировано в ADR-001,
что создаёт два вопроса: (а) residency — можно ли там держать? (б) потеря
какого региона их уронит?

**Решение:**

| Слой | Где живёт | Почему |
|---|---|---|
| **Per-region components** (GoFuture Platform, БД, Kafka, Flink, edge) | В своём регионе | Residency (ADR-001) |
| **DR-реплики** | Вторая зона того же региона | Residency + RTO ≤ 45 мин |
| **Global Control Plane** | **Нейтральная зона EU / Франкфурт** (master) + read-копии во всех 4 регионах | Non-PII; нейтральность; изоляция от потери региона |
| **Global Analytics** | **Та же нейтральная зона EU / Франкфурт** | Non-PII; изоляция; единый ops-контур с control plane |
| **Regional Aggregates → Global** | Batch/S3 из каждого региона в EU | Только хэши (residency не нарушается) |

**Обоснование выбора нейтральной зоны EU/Франкфурт:**
- **Non-PII**: control-plane содержит только схемы, флаги, правила,
  tenant-конфиги, secrets, identity-директорию без PII. Residency
  не блокирует размещение в EU.
- **Политическая нейтральность**: привязка control-plane к одному
  из 4 бизнес-регионов (особенно RU) создала бы политическую
  зависимость и операционные сложности.
- **Изоляция отказов**: упал любой из 4 бизнес-регионов — control-plane
  доступен всем остальным (read-копии локально + master в EU).
- **Зрелость**: зрелая TIER IV инфраструктура, дёшево, GDPR-friendly
  для non-PII метаданных.

**Read-копии во всех 4 регионах:** pull-on-start (при старте сервиса) +
webhook (при изменении). Если нейтральная зона недоступна — регионы
продолжают работать на локальных копиях. Синк флагов/правил
приостанавливается, но сервис не падает.

**Почему Global Analytics в той же зоне, что и Control Plane:** единый
ops-контур (одна команда, один инцидент-канал), один и тот же
compliance-режим (non-PII), одна и та же нейтральность. Разнесение
по разным зонам не даёт выигрыша.

### 3. Диаграмма

Диаграмма репликации — `C2_Replication.puml` (отдельный файл Task3).
На ней:
- 4 boundary регионов, каждый с двумя зонами (`zone 1` + `zone 2`).
- `Regional Edge & Security` в каждом регионе.
- `Regional Externals` (RU — существующие Yandex*, остальные — новые
  платёжные/картографические/банковские интеграции).
- `Global Control Plane` и `Global Analytics` — логические boundary
  над регионами. **Физическое размещение — EU/Франкфурт, согласно
  разделу 2 этого ADR.**
- Красным — новое (репликация, DR, failover, edge, externals новых
  регионов). Синим — существующее из Task1/Task2.

**На диаграмме физическое размещение Global Control Plane и Global
Analytics не отражено** — чтобы не перегружать. Явно зафиксировано
в этом ADR и в README Task3.

### 4. RTO / RPO (assumption)

| Категория | RTO | RPO | Комментарий |
|---|---|---|---|
| **Финансы** (Payments, Payouts) | ≤ 45 мин | ≤ 15 мин | Async streaming replication |
| **Критичные** (Booking, Pricing, Identity, Driver Profile, Driver Status) | ≤ 45 мин | ≤ 1 ч | Async streaming replication |
| **Не-критичные** (Analytics, Notification, Fraud read-path) | ≤ 4 ч | ≤ 1 ч | Warm standby |
| **SEA-PII** | — | **∞** | Потеря Сингапура = потеря PII (принятый риск) |
| **Global Control Plane** | ≤ 30 мин | ≤ 5 мин | Read-копии везде + master в EU |
| **Global Analytics** | ≤ 4 ч | ≤ 1 ч | Batch, не критично к свежести |

**RTO 45 мин достижим только при автоматическом failover** (health checks
+ orchestrator, ADR-004). Ручной failover = 2–4 ч. **RPO 15 мин** требует
  async streaming replication; sync replication неприемлема по latency.

### 5. Что НЕ входит в это решение

- Геомаршрутизация — **ADR-003**.
- Failover-план и таблица сценариев — **ADR-004**.
- Регуляторные детали per-region — **ADR-005**.
- Security-overlay — **ADR-006**.
- Детальный дизайн Kafka-топиков — Task2 ADR-002.
- Механика outbox / DLQ / retry — Task2 ADR-005.
- Инфраструктура (TIER IV, ESXi, Kubernetes sizing) — вне scope ADR.

## Альтернативы

1. **Kafka MirrorMaker для cross-region DR.** Отклонено: Task2 ADR-002
   уже зафиксировал отказ (residency + изоляция отказов). DR — через
   БД-репликацию + восстановление из outbox/processed_events + API-reconciliation.
2. **Репликация PII между регионами (для роуминга).** Отклонено:
   нарушает residency всех 4 режимов. Роуминг — через API к домашнему
   региону (ADR-003).
3. **Sync-репликация для RPO = 0.** Отклонено: неприемлемая latency
   записи (десятки мс → секунды), плюс sync через океан физически
   ограничен скоростью света.
4. **Global Control Plane в одном из 4 бизнес-регионов.** Отклонено:
   создаёт зависимость (упал регион — control-plane недоступен всем),
   политические сложности (особенно RU).
5. **Global Analytics в одном из 4 бизнес-регионов.** Отклонено по той
   же причине + потеря свежести отчётов при потере региона-донора.
6. **Разнести Control Plane и Analytics по разным нейтральным зонам.**
   Отклонено: нет выигрыша, двойной ops.
7. **US (Вирджиния) как нейтральная зона.** Отклонено: политически
   спорно для RU-компонента.
8. **Швейцария как нейтральная зона.** Отклонено: дорого без явной
   ценности по сравнению с EU/Франкфурт.
9. **SEA = Батам как full-DR (с PII).** Отклонено в ADR-001 (PDPA SG +
   PDPA ID). Компромисс — частичный DR.
10. **Реплицировать outbox / processed_events между регионами.** Отклонено:
    операционное состояние per-region. Восстановление — из локальных
    бэкапов + reconciliation с внешними PSP.

## Компромиссы

- **Cross-region PII отсутствует** — роуминг через API даёт latency.
  Митигация: edge-кэш только non-PII (hashed(email/phone), payment_token, home_region) — детали в ADR-003.
- **Kafka cross-region не реплицируется** — при потере региона события
  «в полёте» теряются. Митигация: критичные события материализованы
  в БД (outbox → consumer → processed_events); reconciliation через API
  к внешним PSP + сверка outbox с processed_events после failover.
- **SEA-PII RPO = ∞** — потеря Сингапура = потеря PII (принятый риск).
  Митигация: бэкапы в том же регионе; 99,99% только для AZ-катастроф
  (ADR-001).
- **Global Control Plane в EU** — политическая нейтральность, но
  формально «третья зона» вне 4 бизнес-регионов. Митигация: там только
  non-PII метаданные; read-копии во всех регионах.
- **RTO 45 мин — assumption** — достижим только с автоматическим
  failover (ADR-004). Ручной — 2–4 ч.
- **RPO 15 мин / 1 ч — assumption** — async-репликация не даёт RPO = 0.
  Более строгий RPO требует sync через океан = неприемлемо.
- **Batch для Global Analytics** — задержка до нескольких часов.
  Митигация: для критичных дашбордов — отдельный near-real-time поток
  (пока вне scope, зафиксировано как возможное расширение).
- **Warm standby для не-критичных** — при потере региона RTO 4 ч.
  Митигация: не-критичные не входят в 99,99% SLA.
